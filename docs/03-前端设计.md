## 1. 定位与边界

### 1.1 这个前端是给谁看的

**作品集 / 面试演示**。它需要同时回答三个问题：

1. 审美：能不能做出一个有识别度、不套模板的界面；
2. 工程：能不能把「设计 → 组件 → 接口 → 异常 → 部署」讲成一条线；
3. 克制：知道哪些东西不该做（不引重型 UI 库、不做假动画、不为了炫技加 3D）。

真实产品需要的 SEO、埋点、A/B、多语言、无障碍审计不在本期范围内，但在第 12 节留了扩展位。

### 1.2 本期做（阅读主线）

| # | 页面 | 用户能完成的事 |
|---|---|---|
| 1 | 首页 `/` | 看到继续阅读、本周热读、分类入口、热门推荐、最近更新 |
| 2 | 书库 `/browse` | 按分类 / 状态 / 排序 / 翻页挑书，网格与列表两种视图 |
| 3 | 搜索 `/search` | 关键词搜索、分类与状态筛选、五种排序、高亮命中 |
| 4 | 榜单 `/rank` | 日 / 周 / 月 / 总四榜，前三名重点展示 |
| 5 | 详情 `/novel/:id` | 看简介与评分、加入书架、评分、读目录与书评、跳到相似作品 |
| 6 | 目录 `/novel/:id/chapters` | 浏览全部章节、跳章、看到上次读到的位置 |
| 7 | 阅读 `/novel/:id/chapters/:seq` | 沉浸阅读、上下章、字号 / 行距 / 主题、键盘翻章、进度记忆 |
| 8 | 登录 `/login` | 登录 / 注册、错误提示、演示账号一键填入 |
| 9 | 设计系统 `/styleguide` | 一页看完全部 token 与组件（同时是面试讲解的目录页） |

### 1.3 本期不做（留好口子）

- **书架页 / 个人主页 / 社区前端**：后端接口已就绪，前端下一阶段接；本期只在详情页做「加入书架」的即时反馈。
- **写书评 / 回复**：详情页只读；书评点赞已接真实接口并落库，写书评与回复仍在 P3。
- **管理后台 / 导入工具界面**：导入仍是 `--spring.profiles.active=import` 的命令行动作。
- **SSR / SEO**：见 1.4。

### 1.4 三个明确的取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| SPA 还是 SSR | **Vite SPA** | 阅读站的 SEO 有真实价值，但本期是作品集；SPA 能让「前后端分离 + 同源代理 + 令牌刷新」这条工程线更干净。要 SEO 就换 Next.js，不是加个 `react-helmet` 能解决的 |
| 组件库 | **不引** | 组件库会把页面拉成后台风；这套设计只需要 11 个基础组件，手写比覆盖样式更省 |
| 动画 | **只做状态变化** | 150–300ms 的位移与淡入，不做滚动视差；`prefers-reduced-motion` 下全部关闭 |

## 2. 信息架构与路由

```
夜读
├── 首页
│   ├── 继续阅读（登录后）
│   ├── 本周热读 → 榜单
│   ├── 按题材找书 → 书库（带 category）
│   ├── 热门推荐 → 详情
│   └── 最近更新 → 阅读（最新章节）
├── 书库（分类 / 状态 / 排序 / 视图 / 分页）
├── 搜索（关键词 / 分类 / 状态 / 排序）
├── 榜单（日 / 周 / 月 / 总）
├── 详情
│   ├── 目录（预览 12 章 → 全部）
│   ├── 书评（读，不写）
│   ├── 评分（登录）
│   └── 相似推荐
├── 阅读（沉浸，无站点壳）
├── 登录 / 注册（聚焦，无站点壳）
└── 设计系统（站内）
```

### 2.1 路由表

| 路由 | 组件 | 数据来源（已接入） | 登录 |
|---|---|---|---|

| `/novel/:id` | `NovelDetailPage` | `GET /novels/{id}`、`/chapters`、`/reviews`、`/rating` | 公开（评分/书架需登录） |
| `/novel/:id/chapters` | `CatalogPage` | `GET /novels/{id}/chapters?page&size` | 公开 |

> 只有阅读器与登录页不套 `SiteLayout`：一个要沉浸，一个要聚焦。其余页面共享页头页脚。

### 2.2 导航原则

- 主导航只有 **书库 / 榜单** 两项。社区、书架没有前端页面，就不放进导航——宁可少一个入口，也不给死链接。
- 搜索入口在页头常驻（`lg` 以上是输入框，窄屏是图标），任何页面都能直接搜。
- 当前页用一条 1px 下划线标记，不做大面积高亮。

## 3. 设计语言

### 3.1 品牌

- **名字**：夜读。取「夜里读书」这一场景，和纸白底色、暖光、克制的强调色一致。
- **语气**：像一位不太爱说话的编辑。文案短句、少感叹号，不用「震惊」「必看」。
- **标志**：`夜读` 用衬线体 + 小号 `NOVEL` 字距拉开。没有一个图形 logo——字体本身就是标志。

### 3.2 色彩

颜色全部定义在 `web/src/styles/index.css` 的 `@theme` 里，页面里不允许写死十六进制。

| Token | 值 | 用途 |
|---|---|---|
| `paper` | `#f6f4ef` | 页面底色，带一点暖 |
| `paper-deep` | `#efebe2` | 悬浮态、分区底色 |
| `surface` | `#fffefb` | 卡片、输入框、浮层 |
| `ink` | `#1a1815` | 正文、主按钮 |
| `ink-soft` | `#403b34` | 次级正文 |
| `muted` | `#7b756b` | 辅助信息 |
| `faint` | `#a39c90` | 弱提示、占位符 |
| `line` | `#e4dfd4` | 1px 分隔线 |
| `accent` | `#2e594e` | 链接、选中、强调（松绿） |
| `accent-soft` | `#e6eeea` | 强调色的浅底 |
| `gold` | `#b0873f` | 评分星，只有这一处用金色 |
| `danger` | `#a8483d` | 错误提示 |

**为什么是松绿而不是常见的品牌蓝**：蓝太像后台；松绿接近墨与旧书封皮的颜色，和纸白放在一起更安静。
整站只有一个强调色，金色只服务评分，避免出现「三种强调色互相抢」。

### 3.3 字体

| 角色 | 字体 | 说明 |
|---|---|---|
| 标题 / 正文 | **Noto Serif SC Variable**（自托管） | 衬线体是这套设计的主角；200–900 可变字重 |
| UI / 信息 | **Inter Variable + Noto Sans SC Variable**（自托管） | 按钮、标签、分页、表单；中文不再依赖系统字体 |
| 等宽 | 系统等宽 | 只用于演示账号、错误码 |

- 三款字体都通过 `@fontsource-variable` 自托管，并按 `unicode-range` 切成子集：浏览器只会下载页面实际用到的字。
- **不依赖 `PingFang SC` / `Microsoft YaHei` 是否在场**：设计在不同机器上必须长一样，尤其是截图与演示机。

字号阶梯：

| 级别 | 尺寸 | 行高 | 用在哪 |
|---|---|---|---|
| Display | 52–70px | 1.12 | 首页主标题 |
| H1 | 34–42px | 1.18 | 页面标题 |
| H2 | 22–30px | 1.3 | 章节标题 |
| H3 | 16–19px | 1.4 | 卡片标题 |
| Body | 13.5–15px | 1.9–2.0 | 正文 |
| Small | 11.5–13px | 1.6 | 元信息 |
| Caption | 10.5–11px | 1.4 | 字距 0.2em 以上的小标签 |

### 3.4 栅格、间距与形状

- 容器：`1240px`（首页 / 书库 / 榜单 / 详情）、`1040px`（搜索 / 目录）、`42rem`（阅读正文）。
- 页面左右留白：移动 24px，桌面 40px。
- 间距只取 4 的倍数；分区间距 64–80px，卡片内部 16–24px。
- 圆角：按钮/输入框 6px、卡片 8–10px、封面 3px、胶囊 999px。封面用最小的圆角，像一本纸质书。
- 阴影只有三档：`shadow-card`（卡片）、`shadow-cover`（封面）、`shadow-pop`（浮层）。不用大面积投影。
- 动效：透明度/位移为主，150–300ms，缓动 `cubic-bezier(.22,.61,.36,1)`；尊重 `prefers-reduced-motion`。

### 3.5 封面系统（程序化封面）

演示库里没有封面图（`cover_key` 为空），但小说站的第一眼就是封面。`NovelCover` 的方案是：

1. 用书名 + 作者做 FNV-1a 哈希；
2. 从 10 组「纸墨色」里取一组（松绿、酒红、午夜蓝、赭石、梅紫、铁锈、石板、橄榄、靛青、深青）；
3. 按哈希取三种版式之一：
   - **居中**：分类在左上，书名居中，作者在左下，印章在右下；
   - **顶对齐**：书名靠上，一条细横线，巨大的书名首字水印，印章在右上；
   - **竖排**：书名竖排靠右，一条竖线，作者在左下；
4. 叠一层 SVG 噪点做纸张颗粒，加书脊阴影与整体高光。

同一本书永远得到同一张封面；有 `coverKey` 时优先用 MinIO 真图。小尺寸封面（<72px）会隐藏巨大的水印字，
避免糊成一团墨。

### 3.6 图标

- 只用 `lucide-react`，线宽 1.3–1.6，尺寸 12–18px。
- 图标是装饰时 `aria-hidden`；可点击的图标按钮必须有 `aria-label`。

## 4. 页面设计

### 4.1 首页

**目标**：三秒内让人知道这是读书站、能马上开始找书；给老用户一个「继续读」的台阶。

结构：`Hero → 继续阅读（登录） → 本周热读 → 分类 → 热门推荐 → 最近更新 → 引言带`。

- **Hero**：左侧标题「今晚，读点什么？」+ 搜索框 + 热搜词；右侧三本封面叠放，主封面略微旋转，
  下方一张「本周共读」浮卡。背景是一个巨大的「读」字水印与一层柔光，不抢内容。
- **本周热读**：左边是榜首大卡（封面 + 排名 + 简介 + 热度），右边 2–8 名的紧凑列表；
  切换日/周/月/总时只换数据，不换布局。
- **分类**：4×2 的细线网格，每格是「大类 + 三个子类」，比一排彩色图标更像书。
- **热门推荐**：六本卡片，按 `sort=hot` 取，是阅读、收藏与书评算出来的热度，不再冒充"编辑人工挑选"。
- **最近更新**：两列「书名 + 共几章 + 多久前」。列表接口不返回最近一章的标题，点击进目录，
  不再为六本书各发一次详情请求——详情接口有阅读数副作用。
- **引言带**：整块墨色 + 博尔赫斯的一句话，给长页面一个呼吸点。

### 4.2 书库

**目标**：让人用最少的点击缩小范围，并且随时知道自己筛了什么。

- 左侧分类：8 个顶级分类，当前分类用松绿 + 一个小圆点。演示数据都挂在顶级分类下，
  子类只作为「按题材找书」的说明文字展示，不做筛选——后端按 `category_id` 精确匹配，
  选一个没有书的子类只会得到空页。
- 顶部工具栏：状态（全部/连载/已完结）、排序（最近更新/最新上架/字数/热度）、网格/列表切换。
- 网格四列（移动两列），列表模式多给两行简介，适合慢慢挑。
- 分页每页 12 本；空态提示换分类或状态。
- 移动端：分类横向换行，排序降级为原生下拉，避免一排胶囊挤爆。

### 4.3 搜索

**目标**：让「搜不到」也可解释。

- 页头搜索框在输入时给最多 6 条建议，支持 ↑↓ 选择与 Enter 提交。
- 搜索结果展示引擎返回的高亮片段：`<em>` 用松绿 + 浅色下划线标记。
- 筛选：全部分类 + 8 个大类；状态（不限/连载/完结）；五种排序（相关度/最近更新/最热/评分/字数）。
- **安全**：高亮 HTML 只保留 `<em>`，其余标签与属性全部剥掉，绝不直接插入引擎返回的 HTML。
- 空态：给出「换更短的关键词 / 去掉筛选」的具体建议，并解释「ES 只是副本，MySQL 才是真相源」。
- 没有关键词时：展示热门搜索与一段「搜索是怎么工作的」，让空白页也有信息。

### 4.4 榜单

- 日 / 周 / 月 / 总四个 tab；前三名用大卡，第一张有浅绿底与「榜首」标签；4–10 名用紧凑列表。
- 每张卡都有「开始阅读」的明确入口，不再把入口藏到 hover 里。
- 页面底部写明：日/周/月读 Redis 实时层，总榜读数据库累计分，**尺度不同，只比名次不跨榜比分数**。

### 4.5 详情

**目标**：一屏之内回答「这本书讲什么、值不值得读、从哪开始」。

- 顶部背景取封面的浅色（`wash`），让详情页跟着书走。
- 左封面 + 右信息：标题、作者、状态、评分（大数字 + 星 + 人数）、阅读/收藏/章节/字数。
- 主按钮：已在书架显示「继续阅读 · 第 N 章」，否则「开始阅读」；次按钮「加入书架」。
- 评分：点「给它打分」展开 1–5 星选择器，选完立即反馈；未登录则跳登录并带回跳地址。
- 简介默认三行，可展开；标签在简介下方。
- Tab：目录（前 12 章 + 查看全部）/ 书评（最热 3 条 + 展开更多）。
- 相似推荐：同分类优先，不足用高分书补齐。

### 4.6 目录

- 顶部：封面、书名、状态、总章数、最后更新时间、阅读进度条。
- 工具栏：正序/倒序（只影响当前页展示）、页码、跳转到第 N 章。
- 每页 30 章，三列；当前读到的章节有浅绿底与「读到」标签。
- 跳章输入只接受数字，超出范围不跳转。

### 4.7 阅读器

**目标**：把「读」这件事做到没有阻力。这是整套页面里最值得讲的一页。

- 无站点壳；顶部工具栏向下滚动收起、向上滚动露出；最顶端有一条 2px 阅读进度线。
- 正文：`42rem` 宽、19px、行高 1.95、首行缩进两字、段间距 0.85em；章节标题居中，上下有留白。
- 设置：字号 15–26、行距三档、主题三档（纸白 / 米黄 / 夜间），全部写入 `localStorage`。
- 键盘：`←` / `→` 翻章，`Esc` 回目录；输入框聚焦时不劫持按键。
- 进度：每翻一页把 `novel.reader.progress.{novelId}` 写成当前章，详情/目录据此显示「继续阅读」。
- 夜间模式用独立的 CSS 变量，不靠反色；正文与背景的对比度仍满足 WCAG AA。
- 章节末尾有「本章完」、预计阅读时间与上一章/下一章，不逼用户回顶部。

### 4.8 登录 / 注册

- 左右分栏：左边表单，右边深色书墙 + 一句引言；移动端只留表单。
- 输入框用下划线而不是盒子，减少「后台表单」感。
- 校验规则与后端逐字一致：用户名 `^[a-zA-Z0-9_]{4,20}$`，密码 8–64 位且含字母和数字。
- 错误分两层：字段级错误写在字段下；服务端错误用一条红色提示，并显示错误码（如 `10103`），
  因为后端契约就是「HTTP 200 + 业务码」，前端必须把它翻成人话。
- 演示账号一键填入；账号由后端真实校验，登录后拿到 JWT 双令牌。

### 4.9 设计系统页

- 色彩、字体、字号阶梯、按钮、标签、星级、封面三种版式、骨架/空态/错误态、三种阅读主题、交互原则。
- 这一页不是给用户看的，是给面试官看的：它证明这套界面有 token、有组件边界，不是一页页拼出来的。

## 5. 组件清单

### 5.1 基础（`components/ui`）

## 6. 数据与接口

### 6.1 契约

- 统一响应 `{ code, message, data, traceId, success }`，`code=0` 成功。
- 分页出参 `{ list, total, page, size, hasNext }`；`size` 上限 50（前端请求 30/12/8 都低于上限）。
- 业务失败是 **HTTP 200 + 业务码**；参数错误才是 4xx。前端按 `code` 分支，不按 HTTP 状态猜。
- 时间统一按 `Asia/Shanghai` 解释；接口返回 `2026-11-05T22:10:00` 这种无时区字符串，前端按本地时间格式化。

### 6.2 页面 → 接口 → 字段

| 页面 | 接口 | 关键字段 |
|---|---|---|
| 首页 | `GET /novels?sort=hot&size=6` | `NovelSummaryView` |
| 首页 | `GET /ranks?period=weekly&size=8` | `rankNo`、`score`、`novel` |
| 首页 | `GET /bookshelf`（登录） | `lastChapterSeq`、`totalChapters`、`hasUpdate` |
| 书库 | `GET /novels?categoryId&status&sort&page&size=12` | 同上 |
| 搜索 | `GET /search?q&categoryId&status&sort&page&size=8` | `novelId`、`categoryName`、`highlight` |
| 榜单 | `GET /ranks?period&page&size` | 同上 |
| 详情 | `GET /novels/{id}` | `latestChapterSeq`、`latestChapterTitle` |
| 详情 | `GET /novels/{id}/chapters?page=1&size=12` | `seq`、`title`、`wordCount` |
| 详情 | `GET /novels/{id}/reviews?sort=hot&size=3` | `liked`、`replyCount` |
| 详情 | `GET /novels/{id}/rating` | `avgRating`、`myScore`、`distribution` |
| 目录 | `GET /novels/{id}/chapters?page&size=30` | 同上 |
| 阅读 | `GET /novels/{id}/chapters/{seq}` | `content`、`prevSeq`、`nextSeq` |
| 登录 | `POST /auth/login` | `accessToken`、`refreshToken`、`expiresIn`、`user` |

### 6.3 五个必须写进注释的字段陷阱

1. **评分是 1–5 分制，不是 10 分制**。`avgRating` 由 1–5 分的评分聚合而来，`4.3` 就是 4.3/5；
   页面上的大数字与星星都用它，不要再除以 2。
2. **`GET /novels/{id}` 有副作用**：每调用一次阅读数 +1。所以：不做 hover 预取、不做
   `refetchOnWindowFocus`、详情页只取一次。React 严格模式在开发环境会把 effect 跑两遍，调试时数字会翻倍，
   这不是后端 bug。
3. **`coverKey` / `avatarKey` 是对象键，不是 URL**。前端拼 `VITE_ASSET_BASE + '/' + key`；
   MinIO 的公共读地址一旦换域名，只改一个环境变量。
4. **分类是扁平数组**，需要前端按 `parentId` 拼两层树；`NovelSummary` 只给 `categoryId`，
   分类名要从 `GET /categories` 的结果里查。
5. **`hasNext` 是后端算好的**，不要用 `page * size < total` 在前端再算一遍；两者在 offset 分页下可能不一致。

### 6.4 后端缺口（后续需要补）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| 1 | 没有「我的书评 / 我的帖子」 | 个人主页做不了 | `GET /users/{id}/reviews`、`GET /users/{id}/posts` |
| 2 | 分类没有书籍数 | 首页分类入口不能显示「共 N 本」 | `GET /categories` 增加 `novelCount`，或单独的聚合接口 |
| 3 | 阅读进度只存在书架里 | 未加书架的书换设备就丢进度 | `PUT /novels/{id}/progress` + `GET /novels/{id}/progress` |
| 4 | 榜单没有名次变化 | 不能画 ↑↓ | `RankItemView` 增加 `previousRank`（需要快照对比，成本不低，可不做） |
| 5 | 首页需要 3–4 个请求 | 首屏瀑布 | 不建议加聚合接口：三个接口缓存策略不同，合并后会互相拖累 |

> `GET /users/{id}` 已经返回 `UserDetailView`（资料 + 统计），个人主页的资料部分不缺东西，缺的是「这个人写过什么」。
> 缺口 1–2 是产品阻断；3 是体验优化（当前只对已加书架的书回写进度）；4 锦上添花；5 明确**不补**。
> P1 的阅读主线不依赖这五个缺口。

## 7. 认证与请求层设计

### 7.1 令牌策略

| 项 | 方案 | 理由 |
|---|---|---|
| access token | **只放内存** | 刷新页面即失效，减少 XSS 可窃取的窗口 |
| refresh token | `localStorage` | 刷新后还能恢复会话；代价是 XSS 仍可读。生产环境应换 `httpOnly + SameSite=Lax` Cookie，需要后端配合 |
| 自动刷新 | 启动时用 refresh 换新 access；之后 401 触发 | 双令牌轮换：旧 refresh 用一次就作废，被盗后原用户下次刷新会失败，能暴露 |
| 单飞 | 同一时刻只发一次 refresh，其余请求排队 | 否则 10 个并发 401 会发 10 次 refresh，后 9 次用已作废的 jti，全部失败 |
| 失败处理 | 清空会话 → 跳登录 → 带回跳地址 | 不静默失败，不无限重试 |

### 7.2 请求层

```
request(url, options)
├── 附 Authorization: Bearer <access>
├── fetch → 解析 Result<T>
│   ├── code === 0 → 返回 data
│   ├── code === 40100/10105 → 触发单飞刷新 → 重放一次
│   └── 其他 → 抛 ApiError(code, message, traceId)
└── 网络错误 → 抛 NetworkError（不重试写操作）
```

- **只在 401/10105 重试一次**，避免死循环。
- 写操作不自动重试：点赞、评分、发书评都不是幂等的（后端有幂等键的除外），自动重试会让用户看到双倍计数。
- 所有错误都带上 `traceId`；Toaster 里可展开看到，用户报障时能直接对上后端日志。

### 7.3 服务端状态

P1 已引入 **TanStack Query**（`web/src/api/queries.ts`），理由不是「流行」，而是三件事：

1. 缓存与失效：分类 10 分钟、详情 5 分钟、搜索 15 秒、榜单/书库 30 秒，不同资源不同 `staleTime`；
2. 请求去重：首页多个模块同时要 `categories`，只发一次；
3. 取消：快速切换分类时取消上一个请求。

查询键约定：

```ts
['novels', { categoryId, status, sort, page, size }]
['novel', id]
['chapters', novelId, { page, size }]
['chapter', novelId, seq]
['reviews', novelId, { sort, page, size }]
['ranks', period, { page, size }]
['categories']
['bookshelf']
```

`['novel', id]` 单独设置 `refetchOnWindowFocus: false`、`staleTime: 5 * 60_000`——原因见 6.3 第 2 条。

### 7.4 路由守卫

- 公开页不拦截；只有「加入书架 / 评分 / 点赞」这类动作在未登录时跳 `/login`，并把当前路径放进 `location.state.from`。
- 不做「整个页面级」的强制登录：阅读入口保持公开，新用户先看到内容再决定注册。

## 8. 状态与异常

每个数据页面都必须设计五种状态，不能只画「有数据」那一种：

| 状态 | 表现 | 备注 |
|---|---|---|
| 加载 | 骨架屏（卡片 / 行） | 不用转圈遮罩，避免布局跳动 |
| 空 | 图标 + 一句解释 + 下一步 | 搜索空态要给出「换关键词」而不是「暂无数据」 |
| 错误 | 页面内提示 + 重试按钮 + traceId | 不弹全屏错误页 |
| 部分失败 | 首页某个模块失败时只让该模块降级 | 例如榜单挂了，书库照常 |
| 降级 | 搜索 10601 时显示「搜索服务暂不可用」 | ES 挂了不影响阅读 |

错误码到文案的映射（已实现；页面统一用 `LoadError` 展示后端 message + traceId，登录/注册在表单层另有校验）：

| 码 | 文案 | 处理 |
|---|---|---|
| `10101` | 用户名已被占用 | 注册表单字段级提示 |
| `10103` | 用户名或密码错误 | 登录错误条，不区分账号不存在 |
| `10104` | 账号已被封禁 | 登录错误条 |
| `10105` | 登录凭证无效，请重新登录 | 清会话 + 刷新令牌 |
| `10201` | 小说不存在 | 404 页 |
| `10202` | 章节不存在 | 阅读器内提示 + 回目录 |
| `10401` | 你已经评过分了 | 切换为「更新评分」 |
| `10403` | 只能操作自己发布的内容 | 隐藏删除/编辑入口 |
| `10601` | 搜索服务暂不可用 | 搜索页局部降级，保留筛选 |
| `42900` | 操作太频繁，请稍后再试 | 登录按钮倒计时 |
| `50000` | 系统繁忙，请稍后再试 | 通用错误条 + traceId |

## 9. 阅读器专项

### 9.1 排版参数

| 项 | 值 | 为什么 |
|---|---|---|
| 行宽 | `42rem`（约 672px） | 中文约 28 字/行；再宽眼睛要来回扫 |
| 字号 | 默认 19px，范围 15–26 | 19px 在桌面与 390px 手机上都能读 |
| 行高 | 默认 1.95，三档 1.75/1.95/2.15 | 中文没有词间空格，行距要比英文更大 |
| 首行缩进 | 2em | 中文书面排版习惯；段间距 0.85em 辅助分隔 |
| 标题 | 居中，25–28px | 与正文左对齐形成对比，明确「新的一章」 |

### 9.2 设置与持久化

- `localStorage` 键：`novel.reader.settings`（字号、行距、主题）。
- 进度键：`novel.reader.progress.{novelId}`（章序号）。
- 隐私模式下写入失败时静默降级，阅读不中断。
- P1 登录后：本地进度与书架进度取较新者；加入书架的书以服务端为准。

### 9.3 键盘与移动端

- `←` 上一章、`→` 下一章、`Esc` 回目录；输入框聚焦时不劫持。
- 移动端：工具栏只留返回、主题、Aa；正文左右 24px；不做左右滑动手势（会与系统返回手势冲突）。

### 9.4 性能

- 章节正文一次取完（单章 ≤ 5 万字，接口已有上限），不在客户端分片。
- 翻章时滚动到顶部，不做翻页动画；预取下一章只在用户停留超过 2 秒后触发（P1）。
- 阅读器不需要封面图与字体以外的资源；首屏只有一章文本 + 字体子集。

规则：

- 别名 `@` 指向 `src`，Vite 与 TypeScript 两边都配，缺一个就会在打包时才炸。

### 10.1 构建与环境

```bash
cd web
pnpm install
pnpm dev            # http://127.0.0.1:5173，/api 代理到 8080
pnpm typecheck      # tsc -b
pnpm build          # 产物在 web/dist
```

- `.env.example` 里的 `NOVEL_API_TARGET` 是开发代理目标；`VITE_ASSET_BASE` 是 MinIO 公共读地址。

### 10.2 部署形态

```
浏览器 ──► Nginx
            ├── /            → web/dist（SPA fallback 到 index.html）
            ├── /api/        → Spring Boot :8080
            └── /assets/     → 带 hash，immutable 缓存
```

- **同域部署**，所以后端不需要开 CORS；开发期由 Vite 代理，生产由 Nginx 代理。
- `index.html` 不缓存；`assets/*` 一年 immutable；字体文件带 hash，同样长缓存。
- 如果坚持前后端分域部署，再给后端加 `CorsConfigurationSource`，而不是在前端绕。

## 11. 性能与可访问性

### 11.1 性能预算与实测

| 项 | 预算 | 当前（`pnpm build`） |
|---|---|---|
| JS（gzip） | ≤ 180 KB | **136 KB**（单包，含 React、Router、lucide 按需） |

> CSS 的 94 KB 听着大，但它不是首屏传输量：`@font-face` 只是声明，字体文件按 unicode-range 按需下载。
> 如果把这套页面部署到真实 CDN，应该把字体文件单独设长缓存，并给首屏用到的拉丁子集加 `preload`。

P1 优化项：

- `React.lazy` 拆分阅读器、设计系统页与登录页，首屏再降 20–30 KB；
- 首页榜单/推荐模块的图片（如果接真封面）用 `loading="lazy"` + 固定宽高比，避免 CLS；
- 用 `preconnect` 指向 MinIO（如果封面换真图）。

### 11.2 可访问性

- 所有可点击图标有 `aria-label`；装饰性图标 `aria-hidden`。
- 焦点环统一 2px 松绿；`:focus-visible` 只在键盘导航时出现。
- 文字对比度：`muted` 在 `paper` 上 ≥ 4.5:1；夜间主题正文 `#c6c2ba` 在 `#14151a` 上 ≥ 9:1。
- 星级有 `role="img"` 与「评分 x 分，满分 5 分」的文本替代。
- 尊重 `prefers-reduced-motion`。
- 键盘可完成：搜索、筛选、翻章、调整字号、登录。

## 13. 已知取舍与后续

1. **程序化封面是兜底，不是终态**。它的价值是让演示在没有素材时也成立；真接入封面图后，
   它会退化成 `onError` 的兜底。真实封面需要运营提供，不能靠生成。
2. **登录已接真实后端**。前端不再保存任何演示密码；`bookworm / novel123456` 是后端真实账号。
   refresh 放 localStorage 是为了刷新免登录，生产环境应换 `httpOnly + SameSite=Lax` Cookie。
3. **不做 10 分制**。后端是 1–5 星，前端就显示 4.3/5；为了「看起来像豆瓣」改成 8.6/10 会让数据说谎。
4. **不引组件库**的代价是分页、Toast、弹层都要自己写；收益是视觉不被组件库的默认样式绑架。
   如果团队里有多人协作，这个取舍应该反过来。
5. **不合并首页接口**。三个接口各自缓存、各自降级，合并成一个「首页聚合」会让一次慢查询拖垮整页。
6. **SPA 的 SEO 损失是明确的**。作品集阶段接受；如果这个站要真的被搜到，应该换渲染方式，
   而不是往 SPA 里塞一堆 meta 标签。
