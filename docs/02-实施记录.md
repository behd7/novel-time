### 踩坑记录

**1. Docker Engine 29 与 Testcontainers 1.19.8 不兼容**

- 现象：`Could not find a valid Docker environment`，但 `docker ps` 一切正常。
- 原因：Docker Engine 29.6.1 的 API 版本是 **1.55**，Boot 3.3.5 BOM 带的 Testcontainers 1.19.8（docker-java 3.3.x）握手失败。
- 解决：父 POM 覆盖 `<testcontainers.version>1.21.4</testcontainers.version>`。

**2. Flyway 10 起 MySQL 支持被拆包**

- 现象：启动时报 `Unsupported Database: MySQL 8.0`。
- 解决：显式引入 `org.flywaydb:flyway-mysql`。这是 Boot 3 升级后最常见的踩坑点之一。

**3. MinIO 必须用 path-style 寻址**

- 现象：`S3Presigner` 生成的 URL 形如 `novel.127.0.0.1:9000/...`，DNS 解析失败。
- 解决：`S3Configuration.pathStyleAccessEnabled(true)`，且 **S3Client 与 S3Presigner 必须使用完全相同的 endpoint / region / 凭证**，否则签名对不上。

**4. 镜像拉取**

- Testcontainers 会直接访问 Docker Hub。本机走 `docker.1ms.run` 镜像站，先 `docker pull` + `docker tag mysql:8.0` 到本地，容器启动时才不需要联网。

## 2026-11-03 · M1 用户与认证

### 设计取舍

**1. 为什么是双令牌，不是单 JWT**

单 JWT 有个绕不过去的死结：**没法吊销**。用户点退出、账号被盗、管理员封号，只要令牌没过期就还能用。
所以拆成两个：`access` 30 分钟（短命，泄露窗口小，且无状态扛性能）、`refresh` 7 天（长命，但 `jti` 落在 Redis 白名单，随时可删）。
刷新时旧 `jti` 立即作废（轮换），被窃取的 refresh 用到第二次就失效 —— 这是能提前发现令牌泄露的关键。

令牌里加了 `typ` 声明区分 ACCESS / REFRESH。不加的话，用户可以直接拿 refresh 去调业务接口，
7 天有效期的设计等于白做。

**2. 反用户名枚举的两个细节**

- 用户名不存在和密码错误，返回**同一个错误码与同一句文案**（`10103`）。
- 用户名不存在时**仍然跑一次 BCrypt**（用启动时预热的 dummy 哈希）。
  否则"查无此人"1ms 返回、"密码错"100ms 返回，响应时间本身就是泄漏渠道。

**3. 限流用 Lua**

`INCR` + `EXPIRE` 是两次往返，中间进程挂掉会让 key 永不过期，那个 IP 就被永久锁死。
Lua 在 Redis 单线程里原子执行，没有这个窗口。

**4. 401/403 有两套出口**

Spring Security 的拒绝发生在进入 Controller 之前，此时 `@RestControllerAdvice` 还没机会介入。
如果不管，前端会收到一个空 body 的 401，跟统一响应格式对不上。
所以 `RestAuthenticationEntryPoint` / `RestAccessDeniedHandler` 自己按 `Result` 格式写 JSON，
Controller 内 `@PreAuthorize` 的拒绝则由 `GlobalExceptionHandler` 处理 —— 两条路径，一份契约。

### 踩坑记录

**1. 宿主机 Redis 掉线，整条注册链路 500**

M0 时 `/dependencies` 里 Redis 还是绿的，隔天再跑，Windows 侧 6379 已经没监听了。
注册要写 refresh 白名单，直接抛 `RedisConnectionFailureException`，被兜底处理器变成 500。
解法：compose 里加 `redis` 兜底服务映射 **6380**（避开主机端口，两者可共存），
`application-local.yml` 里写 `spring.data.redis.port: 6380`。主机 Redis 恢复后删掉这行即可回到 6379。

> 教训：Redis 在认证链路里是**强依赖**，不是"缓存挂了降级"那么轻。
> 要么接受登录不可用，要么给写白名单这一路径做本地降级 —— 这里选了前者，因为白名单写不进去等于令牌无法吊销。

**2. 集成测试被自己的限流拦住**

第一版把 `5 次/分钟` 写死在 `RedisLoginAttemptLimiter` 里，而 MockMvc 的所有请求 `remoteAddr` 都是 `127.0.0.1`，
同一个测试类里连跑几次登录就把阈值打满，后面的用例全被 `42900` 挡住。
把阈值与窗口抽成 `AuthRateLimitProperties`（`novel.auth.rate-limit.*`），测试里调到 1000。

**3. 一处断言写反了**

`register_shouldReturnTokens` 里断言昵称兜底为用户名，但请求体里明明传了昵称。
改成断言传入值，另加一个不传昵称的用例专门验证兜底 —— 断言错比代码错更隐蔽。

**4. `@Component` 会让 JWT 过滤器执行两遍**

`JwtAuthenticationFilter` 如果标 `@Component`，Spring Boot 会把它当普通 Servlet Filter 再注册一次，
加上 `addFilterBefore` 那一份，每个请求解析两次令牌。改成手动 `new` 进链，不注册成 bean。

## 2026-11-03 · M2 阅读（小说 / 章节 / 导入 / 书架）

### 设计取舍

**1. 正文和目录分两张表，而且缓存只缓存正文**

`chapter` 是目录（标题、字数、序号），`chapter_content` 才是 MEDIUMTEXT 正文。
如果合成一张表，"查目录"这一步就会把每章几十 KB 的正文一起拉进内存——目录页只需要 20 条记录。

缓存只加在两处：章节正文（读最多、单体最大）和分类树（几乎不变）。
**小说详情刻意不缓存**：一次主键查询 1ms 就回来了，为它维护一套失效逻辑，
收益远小于"改了封面半天不更新"的风险。缓存的收益必须先大于一致性成本。

**2. 阅读数走写缓冲，不走 `UPDATE ... +1`**

详情页每打开一次就更新 `novel.view_count`，热门书会争同一行锁。
改成先 `HINCRBY novel:view:delta`，再由 `ViewCountFlushJob` 每 60 秒把增量合并回库。
代价是库里最多滞后 60 秒，这对阅读数这种指标完全可以接受。
`drain()` 用 Lua 完成"读出 + 删除"，避免两步之间新来的计数被一起删掉。

**3. 导入的章序号按出现顺序重编号**

盗版站转码后"第103章"重复出现三次是常态。如果照抄原文里的数字，
会直接撞 `uk_novel_seq(novel_id, seq)`。所以解析器只看"这是第几个章节标记"，
原文里写的数字完全丢弃。

**4. 书架是物理删除**

`bookshelf` 上有 `uk_user_novel(user_id, novel_id)`。如果取消收藏只把 `deleted` 置 1，
再收藏同一本书就会撞唯一键 —— MySQL 做不到"只对未删除记录唯一"这种条件唯一键。
所以 `BookshelfEntity` **刻意不映射 `deleted` 字段**：MyBatis-Plus 的逻辑删除是按
"实体里有没有这个字段"生效的，没有这个字段，`delete` 就真的发 `DELETE`。
集成测试里专门有一轮"加入→移出→再加入"来锁住这个行为。

### 踩坑记录

**1. 导入跑完了但进程不退**

`spring.main.web-application-type=none` 只是不起 Web 服务器，JVM 不会因此退出。
Lettuce 的连接事件线程和 `@Scheduled` 的调度线程都是非守护线程，进程会一直挂着。
第一次执行时命令挂了 5 分钟直到超时。修法是在 `NovelImportRunner` 末尾显式 `System.exit(exitCode)`，
顺便把"有文件失败"映射成退出码 1，方便脚本判断。

**2. `sort=wordCount` 匹配不上枚举 `WORD_COUNT`**

`"wordCount".equalsIgnoreCase("WORD_COUNT")` 是 false（下划线）。
把两边的下划线都抹掉再比，前端写 `wordCount`、`word_count` 都能用。
这个 bug 集成测试没抓到，因为测试里没传 sort 参数——手工 curl 时才暴露。

**3. 断言 null 字段时用了 `isNull()`，但字段根本不返回**

全局配置了 `spring.jackson.default-property-inclusion: non_null`，
`prevSeq` 这类 null 字段会被整个省略而不是输出 `null`。
`path("prevSeq").isNull()` 对"字段不存在"返回 false，测试会误报。
改用 `hasNonNull()` 才正确。

## 2026-11-04 · M3 评分与书评

### 设计取舍

**1. 评分：明细 + 冗余聚合，绝不 `AVG()`**

`novel_rating` 存"谁打了多少分"，`novel` 上冗余 `rating_sum / rating_count / avg_rating`。
打分时只做一次加减，详情页读的是三个现成字段。如果每次读都 `AVG()`，
书评一多详情页就会变成全表扫描。

代价是聚合值会漂移（事务回滚、并发、手工改库），所以配一个每天凌晨 3:30 的对账任务，
从明细重算并覆盖。**夜里对账、白天增量**，是这类"读多写少但要求准"的统计的标准分工。

**2. MySQL 的赋值顺序坑**

`addRating` 的 SQL 先改 `rating_sum` 与 `rating_count`，最后算 `avg_rating`。
这不是随便排的：MySQL 的 `UPDATE` 多个赋值**从左到右依次生效**，后面的表达式读到的是已经改过的值。
反过来写，`avg_rating` 会用旧的 sum 算，结果永远差一次更新——而且看起来"只是数值偏了一点"，
极难发现。已在 Mapper 里写明。

**3. 书评带星级 = 顺带打分**

发书评时可以传 `score`，服务端会调同一个评分入口。这样"评分"只有一个数据来源，
不会出现"评论显示 5 星、评分区没记录"的错位。代价是发书评这条路要依赖评分服务，
跨了两个聚合——但换来的一致性值得。

**4. 点赞没上缓存**

设计文档里写过"Redis 计数 + 批量落库"，实际改成了数据库原子更新。原因是：
判断"我点没点过"必须查 `like_record` 明细，既然明细已经在库里，计数再放缓存就多了一处
可能对不上的地方，而收益只有几次 `UPDATE` 的差异。**计数缓存的收益必须大于一致性成本**，
这里不满足。

**5. 最热排序带时间衰减**

`(like_count*10 + reply_count*5) / POW(小时数+2, 1.2)`。只按点赞排，一条三年前的老评会永远在首页；
加衰减后老评自然下沉，新书评有机会冒头。

### 踩坑记录

**1. 集成测试里 `myScore` 永远是 0**

断言里请求 `/rating` 时忘了带令牌，而未登录时 `myScore` 根本不返回，
`asInt()` 拿到默认值 0。这类"字段缺省导致的假失败"比逻辑错更难看出来。

**2. 测试用例互相污染评分**

第一版所有用例共用同一本书，`rating_aggregatesAcrossUsers` 断言"恰好 3 人打分"，
但别的用例也在给同一本书打分，一跑就挂。改成每个用例导入一本新书（标题带序号），
评分聚合的断言才有意义。

**3. 导入服务跳过同名书，反而帮了测试**

因为 `NovelImportService` 会跳过同名书，测试里必须给每本书唯一标题，
否则第二次调用拿到的是同一个 id，等于又共用了一本。

### 实测结果（2026-11-04 11:30）

| 场景 | 结果 |
|---|---|
| 三人打分 5/4/3 | avg 5.0 → 4.5 → 4.0，count 1 → 2 → 3 |
| 匿名查汇总 | avg=4.0 count=3 分布 `{3:1,4:1,5:1}`，`myScore` 不返回 |
| u1 5 星改 1 星 | avg=2.67，count 仍为 3 |

## 2026-11-04 · 代码复审问题修复

独立评审跑了 M1–M3 三个提交，提出 5 条问题，全部修复。

### 1. `PUT /users/me` 传空对象返回 500

`UpdateProfileRequest` 的约定是"不传就不改"，所以 `{}` 是合法请求；但全 null 的实体交给
MyBatis-Plus 后，`updateById` 只按非空字段拼 SET，最终生成 `UPDATE user_profile WHERE user_id=?`，
没有 SET 子句直接抛异常。修法是在 `UserRepositoryImpl.updateProfile` 开头判空后**直接返回**——
"什么都没传"语义上就是"什么都不改"。

### 2. 并发首次打分返回 500

原实现靠 `catch (DuplicateKeyException)` 退化成改分，但默认隔离级别是 REPEATABLE READ：
事务第一次查询就固定了快照，撞键后重新查**看不见**对方刚提交的行，于是再插一次、再撞一次、最终 500。
评审用 2 线程 × 6 轮复现了 6/12 的失败率。

修法：`rate()` 显式降到 `Isolation.READ_COMMITTED`，每条语句取新快照，兜底重读能看到真实数据。
复验 12 次并发首评全部 200，0 次 500。

### 3. 越界分页把 total 抹成 0

三处 `if (list.isEmpty()) return PageResult.empty(...)` 把上一行已经算好的真实总数丢掉了，
前端会把"翻过头了"当成"没有数据"。改成 `PageResult.of(List.of(), 真实total, …)`。
涉及书评列表、楼中楼列表、书架列表。

### 4. `user_stat` 计数只维护了一半

书架增删没写 `bookshelf_count`、点赞没写 `like_received`，而 M3 的书评数已经写了，
同一份统计块里口径不一致。补齐两个计数的维护，并在 AGENTS.md 写清"当前由业务代码同步维护、
接 MQ 时要一并去掉"，避免后人分不清是"还没做"还是"漏了"。

### 5. 非法 sort 返回 200

`NovelSort.from` / `ReviewSort.from` 抛 `BizException(BAD_REQUEST)`，而业务异常统一映射成
HTTP 200 + 业务码，于是 `?sort=nonsense` 返回 `200 / 40000`，与"参数/协议错误走 4xx"的约定冲突。
改成抛 `IllegalArgumentException`（已有 400 分支），并把原始提示带回响应。

### 复验

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `PUT /users/me` 传 `{}` | 500 / 50000 | 200，昵称不变 |
| 12 次并发首评 | 6 次 500 | 12 次全 200 |
| `?page=99` 书评 | total 变 0 | total 保持 1 / 2 |
| `?page=99` 书架 | total 变 0 | total 保持 1 |
| 加入/移出书架 | bookshelfCount 恒 0 | 1 → 0 |
| 被点赞 | likeReceived 恒 0 | 1 |
| `?sort=nonsense` | 200 / 40000 | 400 / 40000 |

### 踩坑记录

**1. `next_retry_at <= NOW()` 让投递"卡住 8 小时"**

应用写库用的是应用时区（Asia/Shanghai）的时间，`NOW()` 取的是数据库时区（容器里是 UTC）。
在本地 Windows MySQL 上两者一致，谁也没发现；一进测试容器，刚登记的事件要等 8 小时才"到期"。
修法：比较值由应用传进去（`next_retry_at <= #{now}`），不再假设两边时钟一致。
同类问题顺手修掉了重建补写：水位从"时间"改成 `outbox` 自增 id，彻底不依赖时区。

**2. `DATETIME` 秒级精度会把"现在"四舍五入到未来**

`next_retry_at` 是秒级 `DATETIME`，写入带纳秒的 `LocalDateTime.now()` 时 MySQL 会**四舍五入**：
`.692` 变 `+1 秒`。于是刚登记的变更约有一半概率"暂时不可投递"，表现为投递偶发延迟。
修法：写入侧 `.withNano(0)` 截到秒。这个坑很隐蔽——不是丢数据，只是慢一拍，靠"感觉不对"才查得出来。

**3. `@MapperScan` 只扫了 `persistence.mapper`**

新 Mapper 放在 `infra/event`、`infra/mq` 下，启动报 "required a bean of type OutboxMapper"。
没有放宽扫描范围（那会把 `OutboxMessageSender` 这种普通接口也注册成 Mapper），
而是把 Mapper 挪进既有的 `persistence/mapper` 包——约定比方便重要。

**4. 消费者不能"先记流水再处理"**

流水先提交、索引写失败时，重试会被唯一键判成"已消费"直接跳过，那条数据就永久缺了。
所以顺序反过来：先写索引（带外部版本号，重复写是无害的空操作），再记流水。
`AGENTS.md` 里"消费端先插 `mq_consume_log`"那句是理想写法，在"索引不是事务资源"的前提下必须调整，
已在该文件 2.6 段落里写明实际做法。

**5. ES 是近实时的，测试不能"写完立刻搜"**

默认刷新间隔 1 秒，写完就查会偶发查不到。测试里改成轮询等待（最多 5 秒），
而不是把索引刷新调成实时——后者会让写入吞吐掉一个数量级。"2 秒内可搜到"这个验收标准本来就是这个意思。

**6. 默认调度线程池只有 1 个**

`spring.task.scheduling.pool.size` 默认 1，凌晨重建会把阅读数落库和 Outbox 投递一起卡住。
配到 3（三个任务各一个）。

**7. IK 插件不在官方镜像里**

`elasticsearch:8.13.0` 没有 `ik_max_word`，直接建索引会被拒。做了 `deploy/es/Dockerfile` 把插件烤进去，
并保留 `novel.search.analyzer` 配置项供无插件环境显式退化成 `standard`。实测：

```bash
curl -s -XPOST 'http://127.0.0.1:9200/_analyze' -H 'Content-Type: application/json' \
  -d '{"analyzer":"ik_max_word","text":"诛仙青云志"}'
# 诛 / 仙 / 青云 / 志 —— 中文按词切分，不是单字
```

|---|---|
| 导入一本新书 → 投递 → 可搜 | 导入 `22:58:37.9`，投递日志 `22:58:38.9`，搜索命中含 `<em>` 高亮 |

## 2026-11-05 · M4 复审修复（5 条）

独立评审对 M4 提了 5 条，3 条与"重建/对账的时序"有关，2 条是索引定义的语义没收干净。
修法都贴着"宁可这次失败，也不要悄悄少一条数据"这条线走。

### 1. 重建写入失败仍切别名（P2）

原实现批量写入有错只打日志、照常切别名，旧索引过几轮被清掉，缺的书就再也补不回来。
改成：**写入和收尾补写任何一处失败都整体放弃**——删掉新索引、不切别名、旧索引继续服务。
代价是一次脏数据会挡住整次重建，但它在日志里是响亮的失败，而不是半年后才发现搜索少了几本书。

### 2. 切别名超时会把已生效的新索引删掉（P3）

`switchAlias` 抛异常不等于没生效（可能是客户端超时）。原实现无条件删 `target`，
一旦服务端已切换，等于把线上索引删了，搜索会一直 10601。改成先查别名指向：
已指向 `target` 就按成功处理，只有确实还指着旧索引才删。
另外 `nextIndexName` 改成"往后找第一个不存在的名字"，避免失败重建留下的孤儿索引让下次重建卡在 `resource_already_exists`。

### 3. 对账修正进不了索引（P2）

对账跑在 03:30、重建跑在 02:00，而对账不发事件、`setRatingStats` 也不自增版本号，
修正后的平均分要等到下次评分或次日重建才进索引。
改成：对账时先比"明细重算值"和"库里现值"（比总分与人数，不比四舍五入后的平均分），
**变了才**写库并发 `UPDATED` 事件；`setRatingStats` 同步自增 `version`，否则补发的事件版本没变，会被索引当成重复消息丢掉。
正常日子几乎没有书会命中，等于零成本。

### 4. 索引映射没真正关闭 dynamic（P3）

注释写着"一个 dynamic 都没留"，实际没设。改成 `dynamic: strict`：
给 `NovelDoc` 加字段忘了同步映射时，写入会直接失败进死信，而不是让 ES 猜一个类型占住映射位。
代价是漏改映射会导致同步中断——这是刻意的，比"字段悄悄没被索引"好排查。

### 5. 阅读数与"最热"排序只跟着导入/评分/重建刷新（P3）

讨论后决定**接受滞后**：阅读数按分钟落库不触发同步，索引里的 `viewCount` 是快照，
"最热"排序最多滞后一天。理由是给一个近似指标每分钟重写索引不划算，
真正的热度分在 M5 由榜单任务写入 `hotScore` 接管。这一点写进了 `NovelDoc`、适配器注释、README 与 AGENTS。

### 6. 验证时新发现：别名缺失时写入会把它自动建成同名索引

重建验证时把 `novel_v1/v2` 删掉后启动应用，日志报 `invalid_alias_name_exception`：
ES 里出现了一个**叫 `novel` 的物理索引**。根因是监听器容器在上下文刷新时就启动了，
比 `ApplicationRunner` 更早——队列里残留的消息先被消费，消费者写别名 `novel`，
别名此时不存在，ES 就把它自动建成同名索引；而 ES 不允许别名与索引重名，于是别名永远建不起来。

两处修：初始化从 `ApplicationRunner` 改成 `SmartLifecycle`（`phase = Integer.MIN_VALUE`），
保证先于任何消费动作；`ensure()` 里补一条明确的诊断——发现同名索引时直接告诉运维
"删掉 `DELETE /novel` 再重启，MySQL 里没丢东西"，而不是抛一串 ES JSON。

### 复验

| 场景 | 结果 |
|---|---|
| 别名缺失 + 有同名索引 | 启动日志给出 `存在与别名同名的物理索引 [novel]…删掉它后重启` |
| 删除同名索引后重启 | `已创建搜索索引 novel_v1` → `搜索索引初始化完成 alias=novel index=novel_v1`，映射 `dynamic: strict` |
| 批量写入有错 | `NovelIndexRebuildJobTest.bulkError_abortsWithoutSwitchingAlias` 断言抛异常、`deleteIndexQuietly` 被调用、`switchAlias` 从未调用 |
| 切别名超时但已生效 | 断言不抛异常且不删索引 |
| 切别名失败且未生效 | 断言抛出且删除新索引 |
| 对账修正 | 断言写库 + 发事件；一致时断言两者都没有 |
| `mvn test` | 105 个用例全绿（core 32 / infra 25 / api 48） |

## 2026-11-05 · M5 榜单（日 / 周 / 月 / 总）

### 本次做了什么

| 能力 | 落点 |
|---|---|
| 四张榜（日 / 周 / 月 / 总），带名次、热度分与小说卡片 | `GET /api/v1/ranks?period=daily` |
| 行为实时累加（阅读 / 收藏 / 书评），阅读按人按天去重 | `RedisRankScoreStore`，三个 ZSET + 一个日去重 Hash，一段 Lua |

| 热度分回写 `novel.hot_score` | 总榜扫描时顺带写，**不自增 `version`** |
| 读缓存 | `rank:cache:{period}:{bucket}`，5 分钟，结算后主动删 |

### 设计上的三个决定

**1. 榜单不走 MQ。** `q.novel.rank.agg` 到 M5 结束仍然是空拓扑。
阅读是最高频的写，每读一次就往 outbox 写一行 MySQL，等于用"不丢事件"的代价换一个本来就允许有误差的数字。
实时层改成业务代码直接 `ZINCRBY`，一次 Lua 完成"判重 + 三桶累加 + 补 TTL"。

**2. 总榜不读 ZSET。** `rank:novel:all` 只能从上线那天开始累加，M2 导入的那批书在它眼里是 0 分，
总榜从第一天起就是错的。而 `novel` 表的三个累计列本来就是总榜要的数，还是现成的——
于是日/周/月读实时层，总榜扫库，两条路径在 `HotScoreCalculator` 汇合。

**3. 结算每轮算"今天"和"昨天"两个日期。** 日榜跨天时是两天、各算一次；周榜和月榜在同周期内会归到
同一个 `rank_date`，去重后只剩一次。少了这一步，23:50 之后的行为永远进不了昨天的榜——
而它恰恰是结算前最后、也最热的一段。

### 踩坑记录

**1. `-DfailIfNoSpecifiedTests` 是个不存在的属性**

多模块下用 `-pl novel-core -am test -Dtest=Xxx` 时，`novel-common` 里一个匹配的测试都没有，
构建直接失败。正确写法是 `-Dsurefire.failIfNoSpecifiedTests=false`，属性前面必须带 `surefire.` 前缀。

**2. 新接口忘了进放行名单，7 个集成用例全 401**

`GET /api/v1/ranks` 没加进 `SecurityConfig` 的 `permitAll`，`RankFlowIntegrationTest` 全部红。
这让"榜单免登录"这条契约由测试兜住了——加放行规则之前先跑一次，比上线后才发现好。

**3. `@Transactional` 在"手工搭 MyBatis"的测试里不生效**

`RankSnapshotRepositoryImplTest` 为了不起整个 Spring 上下文，手工搭了
`MybatisSqlSessionFactoryBean` + `HikariDataSource`。好处是 20 秒跑完 5 个用例，
代价是仓储上的 `@Transactional` 只是个注解——测试里 delete 和 insert 各自提交。
所以测试断的是"第二次 replace 之后库里有几行"，而不是"事务回滚"。

**4. 时钟必须能注入**

`RankPeriod.rankDate()` 和"s哪一天"是同一件事。直接写 `LocalDate.now()` 会让测试在 23:59 跑出两个桶。
所以 `RedisRankScoreStore` / `RankService` / `RankRefreshJob` 全部注入 `Clock`，`RankConfig` 里定义
一个 `Asia/Shanghai` 的系统时钟；单测用 `Clock.fixed(...)` 钉死时间点。

**5. 调度线程池从 3 加到 5**

M5 之前已经有 4 个 `@Scheduled`（阅读数落库 / 评分对账 / 索引重建 / Outbox 投递），池子却只有 3。
加榜单任务前先补齐：否则 02:00 重建那几分钟，Outbox 会被排在重建后面，
"写完 2 秒内可搜到"这条直接不成立。
